# ADR-0003: Business logic runs on the client, and Firestore rules enforce it

- **Status:** Accepted. Derived from [ARCHITECTURE.md](../../project/ARCHITECTURE.md), [D-017](../../project/DECISIONS.md#d-017--void-never-delete-owner-edits-recorded-too) and [D-019](../../project/DECISIONS.md#d-019--one-stored-due-per-bill-paymentdue).
- **Context:** There is no server ([ADR-0002](ADR-0002-firebase-spark-no-backend.md)), but money data must not be tampered with or lost.
- **Decision:** All calculation is pure client code in `utils/calc/*`, `money`, `business-metrics`, `finance-calc`, `labour`, `statements` and `rentals/rent-math`, with oracle and mutation tests. `firestore.rules` (about 2.4k lines) is the only server-side check. It covers roles read from `users/{uid}` (owner, manager or staff, plus status) rather than custom claims, edit windows, void-before-delete (active bills are only voided; an owner may then delete a voided bill and its edit records), money shape, counters, append-only audit and no back-dated cash.
- **Rationale:** This keeps the app on Spark with one source of truth per number (`metric-registry.js`).
- **Consequences:** Every rule check calls `get()` on the user doc, which costs reads. Some page permissions are enforced only in the UI ([role-permissions.md](../../role-permissions.md)). Party dues and stock are derived from bills, not stored. The emulator suite `rules-tests/test.js` runs on every PR (`ci.yml`) and gates the production rules deploy (`firestore-rules-deploy.yml`). `bahi-dev-deploy.yml` publishes rules to the test project without re-running it.
